  2. Overflow Flag (OF) =

The cmp al, bl instruction performs an implied subtraction: al - bl.

  • AL: 1111 0000b
  • BL: 0000 1111b

Intel x86 implements SUB by adding al to the two’s complement of bl. Two’s complement of 0000 1111b is 1111 0001b.

1111 0000b (al) + 1111 0001b (-bl) = 1110 0001b –> Carry_in_MSB=1, Carry_out = 1

  1. Carry Flag (CF): For subtraction, the CPU inverts this carry-out to set the Carry Flag, so CF = NOT(carry_out) = 0.

  2. Overflow Flag (OF): The overflow flag is set if the sign of the result is incorrect in a signed operation. We are subtracting a positive number from a negative number: (-16) - (15) = -31. The result -31 (1110 0001b) fits within an 8-bit signed integer range (-128 to 127). Since the result is correct and did not overflow, the OF is 0. In the lecture, we mentioned OF = Carry_in_MSB XOR Carry_out = 1 XOR 1 = 0.

The standard way to translate an if-else statement is:

  1. Evaluate the condition.
  2. If the condition is false, jump to the ELSE block.
  3. Otherwise, execute the THEN block.
  4. After the THEN block, unconditionally jump over the ELSE block to the end.

Let’s analyze the options:

  • Option 1: jge ELSE jumps if val >= 100. This jumps to the else part when the if is true, which is incorrect.
  • Option 2: jl ELSE jumps if val < 100. This is the opposite of val >= 100, so this is the correct condition to branch to the ELSE part. If the jump is not taken (val is indeed >= 100), the THEN block (mov DWORD [val], 0) is executed, followed by an unconditional jmp ENDIF to skip the ELSE block. This is a perfect implementation.
  • Option 3: This is also a correct implementation. It jumps to the THEN block if the condition is true. The logic is sound.
  • Option 4: This implementation lacks the jmp ENDIF after the else block logic, so if val < 100, it would increment count and then incorrectly fall through to mov DWORD [val], 0.

Comparing Option 2 and 3, both are logically correct. However, Option 2 follows the template provided in example exm-31 from the lecture notes (jnl ELSE, which is jge ELSE). Let me re-read exm-31: if (value < 10) ... else ... is translated with jnl ELSE (which means jge ELSE). So, it jumps to ELSE if the condition is false. The condition is value < 10, its opposite is value >= 10. jnl (Jump if not less) is equivalent to jge. So jnl ELSE is correct.

Now, let’s re-apply that to our question: if (val >= 100). The opposite is val < 100. The jump instruction for “less than” for signed integers is jl. So, jl ELSE is the correct instruction to jump to the ELSE block. This makes Option 2 correct.

if ( (eax > ebx) && (ecx != 0) ) {

    je    ENDIF

    test  ecx, ecx
    jz    ENDIF
    ; Body

For a logical AND (&&), the execution stops as soon as one condition is found to be false (short-circuiting). In assembly, this means if the first condition (eax > ebx) is false, we should immediately jump to the end. If it’s true, we then check the second condition. If that is false, we jump to the end. Only if both are true do we execute the body.

  • Option A & C: This is the most efficient implementation. cmp eax, ebx followed by jle ENDIF correctly jumps out if the first condition (eax > ebx) is false. If not, it proceeds to check the second condition. test ecx, ecx followed by jz ENDIF jumps out if ecx is zero (i.e., ecx != 0 is false). If both checks pass, the code falls through to the body. Both test ecx, ecx and cmp ecx, 0 achieve the same goal of checking for zero. Both are correct.
  • Option B: This is logically correct but unnecessarily verbose with extra jumps.
  • Option D: This is also verbose. It jumps to CONTINUE if the first condition is true, then jumps to ENDIF if the second is false. It’s correct but less efficient than the first option’s fall-through logic.

The following code attempts to implement a nested loop. The outer loop should run 10 times, and the inner loop should run 5 times for each outer iteration.

        mov   ecx, 10   ; Outer loop count
OUTER:
        ; ... some work ...
        mov   ecx, 5    ; Inner loop count
INNER:
        ; ... some work ...
        loop  INNER
        loop  OUTER

What is the primary issue with this code?

The loop instruction exclusively uses the ecx register as its counter.

  1. The outer loop starts by setting ecx to 10.
  2. Inside the OUTER loop, the code immediately overwrites ecx with 5 for the inner loop.
  3. The inner loop runs 5 times, decrementing ecx to 0.
  4. After loop INNER finishes, ecx is 0.
  5. The instruction loop OUTER is then executed. It decrements ecx (from 0 to -1) and checks if it’s non-zero. Since it is non-zero, it jumps to OUTER.
  6. Back at OUTER, ecx is immediately reset to 5, and the process repeats.

The outer loop’s original counter (10) is lost as soon as the inner loop begins. The outer loop will not execute 10 times as intended.
